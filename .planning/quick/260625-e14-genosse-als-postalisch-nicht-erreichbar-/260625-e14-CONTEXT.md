# Quick Task 260625-e14: Genosse als postalisch nicht erreichbar markieren - Context

**Gathered:** 2026-06-25
**Status:** Ready for planning

<domain>
## Task Boundary

Möglichkeit schaffen, ein Mitglied (Member) als postalisch nicht erreichbar zu
kennzeichnen, damit bei späterem postalischen Versand klar ist, dass die Adresse
unzustellbar ist. Quelle: `.planning/todos/pending/member-postal-unreachable-flag.md`.

**Scope dieser Quick-Task:** Datenmodell (neues Status-Feld auf Member) + Audit-
Integration + Frontend-Bedienung. Die tatsächliche Berücksichtigung in den
Versand-Flows (RepaymentLetter, Brief-Bulk-Mail, GV-Einladungen) ist bewusst
ausgeklammert und wird ein separater Folge-Task.

</domain>

<decisions>
## Implementation Decisions

### Datenmodell — Status-Enum (nicht Bool)
- Neues **Status-Enum** auf Member (erweiterbar), **nicht** ein einfaches Bool-Flag.
- Vorerst nur zwei Varianten: `Erreichbar` (Default) und `Unzustellbar`.
- Bewusst erweiterbar gehalten, damit später Gründe wie `Umgezogen`, `Verstorben`,
  `KeinVersandErwünscht` ergänzt werden können — ohne erneute Bool→Enum-Migration.
- **Vorbild:** `MemberStatus`-Enum in `genossi_dao/src/member.rs:37-66`
  (Pattern: DAO-Enum + `MemberStatusTO` in `genossi-frontend/rest-types/src/lib.rs:150-180`
  mit `all()`, `as_str()`, `from_str()`, `display_name()`; Migration als
  `TEXT DEFAULT 'Erreichbar'`).
- Default für Bestandsdaten: `Erreichbar` (alle bisherigen Mitglieder gelten als erreichbar).

### Audit-Pflicht
- Member ist eine **auditierte Entität** → Änderung des neuen Feldes MUSS über
  `audited_update!` laufen, nicht via direktem `member_dao.update`.
- Das neue Feld MUSS in `Member::audit_fields()` aufgenommen werden
  (`genossi_dao/src/auditable.rs` / Auditable-Impl von Member), damit Statuswechsel
  in der Audit-Hashchain landen.

### Migration
- Neue Spalte in `migrations/sqlite/` als `TEXT DEFAULT 'Erreichbar'` (analog
  `20260411000002_add_status_to_member.sql`). Nullable/Default sodass bestehende
  Daten kompatibel bleiben.

### Versand-Verhalten (Richtungsentscheidung, NICHT Teil dieser Task)
- Wenn die Flows später integriert werden: markierte Mitglieder sollen **gewarnt/
  gekennzeichnet** werden (Pre-Flight-Liste analog
  `[[backend-pre-flight-check-attach-repayment-letter]]`), **nicht hart
  herausgefiltert** — der Vorstand entscheidet manuell. Diese Richtung ist
  festgehalten, wird aber in dieser Quick-Task NICHT umgesetzt.

### Frontend
- Auswahl (Select/Dropdown analog Member-Status) auf der Member-Detail-Seite
  (`genossi-frontend/src/page/member_details.rs`, Status-Select bei ~Zeile 590-610).
- **Component-First** — kein inline-RSX-Duplikat; falls ein passender Select-Baustein
  existiert, wiederverwenden, sonst in `genossi-frontend/src/component/` extrahieren.
- i18n-Keys analog `Key::MemberStatus*` in `genossi-frontend/src/i18n/` ergänzen
  (de.rs Übersetzungen für `Erreichbar` / `Unzustellbar`).

### Claude's Discretion
- Konkreter Feldname / Enum-Name (Vorschlag: `PostalStatus` mit Spalte
  `postal_status`, analog `MemberStatus`/`status`) — Planner darf passend zur
  Codebase wählen.
- Genaue Platzierung des Selects im Member-Detail-Formular.

</decisions>

<specifics>
## Specific Ideas

- Enum-Pattern strikt nach `MemberStatus` / `MemberStatusTO` spiegeln, damit das
  Frontend dieselbe `all()`/`display_name()`-Mechanik nutzen kann.
- Default-Wert `Erreichbar` überall, wo der bestehende `MemberStatus` `Normal` als
  Default verwendet.

</specifics>
