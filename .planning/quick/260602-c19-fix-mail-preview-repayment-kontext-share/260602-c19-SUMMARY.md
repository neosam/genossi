# Quick-Task 260602-c19: Mail-Preview-Repayment-Kontext-Share Summary

**One-Liner:** POST /api/mail/preview liest jetzt echte RepaymentEntries pro Member statt hartkodierter Dummy-Werte und spiegelt die Worker-Aggregations-Logik (worker.rs:332-361) als read-only Pfad — End-to-End-getestet gegen den c19-Bug-Symptom.

## Objective

Bug-Fix: `POST /api/mail/preview` rief im Repayment-Kontext (`body.repayment_phase_id` gesetzt) `merge_repayment_context(base_ctx, "60,00", 1, 2026)` mit hartkodierten Dummies auf — die Vorschau zeigte für jedes Mitglied `share_count=1`, unabhängig vom DB-Stand. Send-Pfad (Worker) war nicht betroffen.

## Root Cause

Der Preview-Handler in `genossi_mail/src/rest.rs:494-508` enthielt seit UAT-Defekt #6 (Phase 12) einen Sentinel-Code-Pfad: damit der Render bei aktivem Repayment-Kontext nicht an "undefined value" scheiterte, wurden konstante Dummy-Werte `("60,00", 1, 2026)` gemergt. Diese sollten später durch echte Per-Member-Aggregation ersetzt werden — wurden aber nicht.

Der Send-Worker (`genossi_mail/src/worker.rs:332-361`) machte es korrekt:
- `repayment_entry_dao.find_by_phase_id(phase_id, tx)`
- Filter: `deleted IS NULL && member_id == m.id && status IN (Open, Contacted)`
- Summe: `share_count_to_pay_out`
- Format: `format!("{},{:02}", cents/100, cents%100)`

→ Vorschau und Versand divergierten. Was-du-siehst != was-du-sendest.

## Fix-Strategie

**Option A** (in Debug-Doku empfohlen): Preview an Worker-Logik angleichen — Aggregation 1:1 duplizieren statt refaktorieren.

Begründung für Duplikation: Scope-Disziplin (Quick-Fix soll Worker-Code nicht anfassen). Tech-Debt für späteren Refactor dokumentiert.

## Implementation

### Files Modified

**1. `genossi_mail/src/rest.rs` (+24 / -7 LOC)**

- `MailRestState`-Trait um Methode `resolve_repayment_context(phase_id, member_id) -> Option<(payout_amount: String, share_count: i32, fiscal_year: i32)>` erweitert (Signatur-Stil 1:1 wie bestehende `resolve_member`).
- `preview_mail`-Handler patcht den Repayment-Branch:
  - UUID-Parse-Error → `MailServiceError::BadRequest("Invalid repayment_phase_id")` → HTTP 400 (T-c19-05 Mitigation).
  - Echte Aggregation via `state.resolve_repayment_context(phase_id, member_id).await`.
  - `None` → `base_ctx` (D-05-Symmetrie; Template muss `{% if defined %}`-Guard verwenden).
- `PreviewRequest.repayment_phase_id` Doc-Comment komplett überarbeitet: keine Erwähnung von "Dummy"/"60,00"/"1" mehr, verweist auf worker.rs als Source of Truth.

**2. `genossi_bin/src/lib.rs` (+62 LOC)**

- Neue Trait-Methode `RestStateImpl::resolve_repayment_context` implementiert direkt nach `resolve_members` in `impl MailRestState for RestStateImpl`.
- Folgt dem `resolve_member`-Pattern: pool clonen, lokale `TransactionDaoImpl` + `RepaymentPhaseDaoImpl` + `RepaymentEntryDaoImpl` konstruieren, `tx` eröffnen, `ok()?` für Fehler-Swallowing (read-only Preview soll bei DB-Fehler eher silent leer rendern als 500).
- Tx-Reuse: `phase_dao.find_by_id(phase_id, tx.clone())` + `entry_dao.find_by_phase_id(phase_id, tx)` — `TransactionImpl` ist Clone-able.
- Filter identisch zu worker.rs: `e.deleted.is_none() && e.member_id == member_id && matches!(e.status, Open | Contacted)`.
- Summe + Format identisch zu worker.rs: `format!("{},{:02}", cents/100, cents%100)`.
- `share_count == 0` → frühes `return None` (D-05-Symmetrie).

**3. `genossi_bin/tests/e2e_tests.rs` (+136 LOC, 2 Tests)**

- `test_mail_preview_repayment_share_count_aggregates_real_value`: Setup mit Member current_shares=3 + Auto-Fill-Phase share_value=12000; assertet rendered_body enthält "Anteile: 3,", "360,00", "2026" und nicht "Anteile: 1,".
