<objective>
Migrate all three MailBodyEditor call sites to WysiwygEditor, wire the second-body signal (`body_html`) end-to-end from each editor host through to the API layer, and extend TemplatePreview so it renders the backend-provided HTML preview when available. After this plan, no code in the frontend uses MailBodyEditor and the body_editor.rs file is deleted.

Purpose: Consolidate the migration into one plan so a single reviewer can see all three call-site edits + the TemplatePreview extension side-by-side. Keeping this as its own plan (not folded into 24-02) preserves the ~50% context budget: 24-02 is heavy Dioxus/web-sys, 24-03 is heavy Signal + API-plumbing edits across 8 files.

Output: All three MailBodyEditor call sites replaced with WysiwygEditor. Compose-Page, Reply-Form, and Template-Editor each hold a second `_body_html` signal that flows through to the send/reply/save-template APIs and is displayed in the extended TemplatePreview. body_editor.rs is deleted; mod.rs is updated. Backwards-compat rule: when the editor produces an empty innerHTML (user typed only plain text with no formatting), the send/reply path posts `body_html: None` so Phase 23's `create_job` stores NULL and legacy text-only behavior is preserved for that specific send.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| WysiwygEditor DOM → Dioxus signals → API | The user-authored HTML crosses two Rust boundaries (signal → send helper → HTTP body) before hitting the backend sanitize gate |
| TemplatePreview response HTML → Dioxus DOM | The backend-rendered HTML string is injected into the DOM via dangerous_inner_html — must be rendered by the autoescape env, not a plain string template |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-24-07 | Tampering | Preview HTML via dangerous_inner_html | high | mitigate | The rendered body_html comes from the backend's render_html_template with autoescape env (Phase 23 D-04). Member-supplied values are HTML-escaped; author markup passes as structured tags. The frontend NEVER renders raw body_html the user just typed — only the backend-rendered response. Frontend-side sanitization is not a security boundary (Phase 23 established that; ammonia is server-side). |
| T-24-08 | Tampering | Empty-HTML → None wire | low | mitigate | The `if body_html.trim().is_empty() { None } else { Some(...) }` rule ensures legacy text-only sends stay text-only (Phase 23 HTML-03 backward-compat). Prevents accidentally-empty body_html from being sanitized-to-empty and then rendered as an empty HTML mail part. |
| T-24-09 | Information Disclosure | Submit-Guard DOM read | low | accept | Reading .innerHTML/.innerText from the editor's own DOM node is same-origin same-component — no cross-frame or cross-component exposure. |
</threat_model>
