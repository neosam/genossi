# Phase 32 — UI Design Contract

> Visual and interaction contract for the Application Compose-Dialog. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Design-system source of truth: the existing `genossi-frontend` codebase.** This phase invents NO new
> design system. It reuses `component/mail_compose/*`, the unchanged `communication_timeline.rs`, the
> `Modal` component, and the button/toast/error patterns established in `mail_page.rs` and
> `member_details.rs`. All tokens below are *extracted from* that codebase, not proposed anew.

**Reused components (do NOT re-style, do NOT fork):**
- `component/mail_compose/`: `MailSubjectInput`, `WysiwygEditor` (+ `plain_to_html`), `TemplateSelector`, `TemplatePreview`, `MailPreviewFrame`, `TemplateVarButtons`, `MailAttachmentPicker`
- `component/communication_timeline.rs` — `CommunicationTimeline(entries: Vec<CommunicationEntryTO>)`, unchanged/prop-driven (click→body added additively per D-06; if not prop-extendable without breaking the Member usage, use a thin wrapper)
- `component/modal.rs` — `Modal` (used for the body-detail panel if the modal variant is chosen over inline-expand)
- `component/toast.rs` — `ToastContainer` + `show_toast` (post-send success)
- `component/error_alert.rs` — `ErrorAlert { error, on_dismiss }` (send failure)
- `TopBar` page chrome

**Layout skeleton for the new Compose page (mirror `page/mail_page.rs`):**
`RequirePrivilege(PRIVILEGE_ADMIN)` → `div.flex.flex-col.min-h-screen` → `TopBar` → `div.flex-1.container.mx-auto.px-4.py-8` → `h1.text-3xl.font-bold.mb-6` title → success/error banners → compose card `div.bg-white.rounded-lg.shadow.p-6.mb-6`.

**Visual hierarchy / focal point:**
- **Compose page:** the resolved live preview (aufgelöste Platzhalter) is the **primary focal point** — it is
  the artifact the user reviews before committing (D-05: the preview IS the confirmation). The **"E-Mail
  senden" button** is the **secondary anchor** (sole blue accent, bottom of the compose card), and the
  prominent "zuletzt gesendet" line sits directly above/beside it as the anti-double-send cue.
- **`application_detail` additions:** the **"✉ E-Mail senden" button** is the primary anchor of the new
  block (sole blue accent); the "zuletzt gesendet" summary is its secondary supporting line, and the
  communication timeline reads as a calm tertiary section below.

## Spacing Scale

**Target contract: the standard spacing set only — {4, 8, 16, 24, 32, 48, 64}px.** Every value this phase's
NEW markup declares is drawn from that set (all multiples of 4):

| Token | Value | Tailwind | Usage in this phase |
|-------|-------|----------|---------------------|
| xs | 4px | `gap-1` `mt-1` `py-1` | Icon/label gaps, chip internal gap, status-badge vertical padding |
| sm | 8px | `gap-2` `py-2` `mb-2` `space-x-2` | Compact element spacing, button vertical padding |
| md | 16px | `p-4` `mb-4` `space-y-4` `px-4` | Default element/section spacing, form field stack, cell/button horizontal padding |
| lg | 24px | `p-6` `mb-6` | Card interior padding, section breaks |
| xl | 32px | `p-8` | Modal interior padding (`Modal` component) |

Status badges in this phase's new markup use **`py-1` (4px)** vertical padding — a standard-set value that
needs no code exception.

### Inherited pre-existing drift (out of this phase's remit)

These non-standard values live in reused, un-forked components; this phase inherits them verbatim but does NOT
introduce, expand, or re-declare them as first-class tokens:
- **`py-0.5` (2px)** — vertical padding inside the existing status badges of `communication_timeline.rs`,
  reused unchanged. This phase's own badge markup uses `py-1` (4px, above); the 2px value only appears where
  the pre-existing timeline component renders it.
- **`px-3` (12px)** — horizontal cell/button padding inside reused table/button components (e.g. existing
  `px-4 py-3` table cells). Not in the standard set; not introduced by this phase. New markup uses `px-4`
  (16px). The 12px value is pre-existing codebase drift out of this phase's remit.

## Typography

**Target contract: 4 sizes, 2 weights.** This phase's NEW surfaces (Compose page, the `application_detail`
additions) declare exactly four sizes — **30 / 20 / 14 / 12** — and two weights: **`font-bold` (700)** for the
display title and primary CTAs, **`font-medium` (500)** for everything else (labels, headings, meta emphasis).

| Role | Size | Weight | Line Height | Tailwind |
|------|------|--------|-------------|----------|
| Display (page title) | 30px | 700 bold | ~1.2 (Tailwind default for 3xl) | `text-3xl font-bold` |
| Heading (card / section / dialog-panel) | 20px | 500 medium | ~1.4 | `text-xl font-medium` |
| Label | 14px | 500 medium | 1.5 | `text-sm font-medium text-gray-700` |
| Body / table cell | 14px | 500 medium | 1.5 | `text-sm` |
| Meta / caption | 12px | 500 medium | 1.4 | `text-xs` (timeline date, status badges, hints `text-xs text-gray-500`) |

Note: the former "Heading" (20px) and "Sub-heading" (18px) roles are merged into a single 20px heading role
(`text-lg`/18px is NOT introduced by this phase) so the declared size scale stays at four.

Body copy default: **14px (`text-sm`) at weight 500, line-height 1.5.** Rendered mail body in the detail
panel uses `text-sm whitespace-pre-wrap` inside a scroll container (see UI Considerations → long-text).

### Inherited pre-existing drift (out of this phase's remit)

The reused, un-forked components carry weight/size values this phase does NOT introduce, expand, or restyle —
they are pre-existing codebase drift inherited verbatim from `component/*`:
- **`font-semibold` (600)** on some existing headings and **`font-normal`/regular (400)** as the browser
  default inside reused inputs, timeline rows, and the `Modal` chrome. Where this phase writes new markup it
  uses only 700/500; it does not remove or re-declare 600/400 inside components it reuses unchanged.
- The contract TARGET remains **2 weights / 4 sizes**. Any 600 or 400 that appears at runtime originates in
  reused components, not in this phase's own additions.

## Color

The app's palette is Tailwind's default named scale on a white/gray canvas with a blue accent. No hex
overrides for these roles exist — values below are the Tailwind reference hexes for the classes actually used.

| Role | Value | Tailwind | Usage |
|------|-------|----------|-------|
| Dominant (60%) | `#ffffff` | `bg-white` | Page + card/panel surfaces |
| Secondary (30%) | `#f9fafb` / borders `#d1d5db`,`#e5e7eb` | `bg-gray-50`, `border-gray-200/300` | Table headers, subtle panels, section backgrounds, input borders |
| Accent (10%) | `#3b82f6` / `#2563eb` | `bg-blue-500`/`hover:bg-blue-600`, `bg-blue-600`/`hover:bg-blue-700`, `text-blue-600`, `focus:ring-blue-500` | See reserved-for list below |
| Destructive | `#ef4444` / `#dc2626` | `bg-red-500`/`hover:bg-red-600`, `text-red-*` | Not triggered by this phase's happy path; present via `ErrorAlert` (send failure) and `failed` status badge |

Accent (blue) reserved for:
1. The primary **"E-Mail senden"** submit button on the Compose page (`bg-blue-500 hover:bg-blue-600 text-white`).
2. The **"✉ E-Mail senden"** button on `application_detail.rs` (`bg-blue-600 hover:bg-blue-700 text-white`, mirrors `member_details.rs`).
3. Text links (subject links in the timeline, "back" link) — `text-blue-600 hover:underline`.
4. Input focus rings — `focus:ring-2 focus:ring-blue-500`.

Accent is NOT applied to generic containers, non-primary buttons (those use `bg-gray-200 hover:bg-gray-300 text-gray-700`), or the "zuletzt gesendet" info line.

Semantic status colors (established, badge-only — reused verbatim from `communication_timeline.rs`, do not redefine):
| Status | Classes |
|--------|---------|
| sent / done / success | `bg-green-100 text-green-800` |
| failed | `bg-red-100 text-red-800` |
| pending | `bg-yellow-100 text-yellow-800` |
| no-email warning | `text-amber-600` / `bg-amber-100 text-amber-800` |
| success banner (post-send) | `bg-green-100 border-green-400 text-green-700` |

## Copywriting Contract

App language is **German** (primary locale `De`; every key must also exist in `En`). Exact i18n key names are
Claude's Discretion (CONTEXT.md); reuse existing keys where they exist, add new ones for the italicized copy.

| Element | Copy | i18n key |
|---------|------|----------|
| Primary CTA (Compose page) | "E-Mail senden" (+ shows "Sende…" / `MailSending` while the request is in flight) | `Key::MailSend` / `Key::MailSending` (existing) |
| Trigger button (application_detail) | "✉ E-Mail senden" | `Key::MailSendButton` (existing) |
| Disabled-button annotation (no email) | "Keine E-Mail-Adresse hinterlegt" — button `disabled` + `title` + italic gray hint beside it | `Key::NoEmailAddressHint` (existing) |
| "zuletzt gesendet" line | *"Zuletzt gesendet: {Betreff} — {Status} am {Datum}"* — must show **subject + status + date**, shown BOTH beside the detail-view button AND prominently on the Compose page (anti-double-send guard) | *new key* (e.g. `Key::LastSentSummary`) |
| Empty state (timeline) | "Noch keine Kommunikation" (existing empty render: `p.text-gray-500.italic`) | `Key::CommunicationNone` (existing) |
| Empty state (no "zuletzt gesendet" yet) | *"Noch keine E-Mail gesendet"* — italic gray, shown where the last-sent line would be when history is empty | *new key* (e.g. `Key::NeverSent`) |
| Error state (send failed) | Rendered via `ErrorAlert` — shows the backend `AppError` message + dismiss; problem is surfaced, never a silent 200 (APMAIL-02) | existing `ErrorAlert` |
| Success (post-send) | "E-Mail-Auftrag erstellt" → green success toast/banner, then navigate back to detail view | `Key::MailJobCreated` (existing) |
| Body-detail panel title | *"Gesendete E-Mail"* — panel/modal heading over the real stored body | *new key* (e.g. `Key::SentMailBody`) |

Destructive / irreversible actions in this phase:
- **Sending the email is the single confirm-gated action.** Per D-05 there is **no separate confirm modal**:
  the resolved live preview IS the confirmation, and the deliberate click on "E-Mail senden" satisfies
  confirm-before-send (APMAIL-04). The send button is `disabled` while the request runs (`disabled: *sending.read() || subject.is_empty()`) to prevent double-send. The Dioxus `form onsubmit` reload
  trap is avoided via `div` + `onclick` + `r#type:"button"` (pattern from `repayment_phases.rs`).
- Viewing a sent body is **read-only** (real stored `rendered_body`/`rendered_html_body`, never re-rendered).

## UI Considerations

Shape-rooted UI *state* coverage for the Compose page and the `application_detail` additions. Empty/error
COPY lives in the Copywriting Contract above; rows here reference it rather than restate it.

Applicable state considerations resolved: 7 covered, 1 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | communication timeline (list-collection) | ✅ covered | Empty entries render the documented `CommunicationNone` italic-gray copy (existing component behavior). |
| empty | "zuletzt gesendet" line when no mail ever sent (static-content) | ✅ covered | Renders the documented `NeverSent` italic-gray copy in place of the last-sent summary; button stays enabled (if email present). |
| loading | live preview during debounce (async-fetch) | ✅ covered | Debounced call to the Phase-31 application preview endpoint; while pending, keep the last resolved preview visible (no fl?icker/empty flash); debounce timing is Claude's Discretion per D-04. |
| loading | send in progress (form-submit) | ✅ covered | Send button `disabled` + label swaps to `MailSending`; prevents double-send (D-05). |
| error | send failure (async-fetch) | ✅ covered | `ErrorAlert` surfaces the real backend error with dismiss (APMAIL-02) — see Copywriting error row. |
| partial | recipient without email address (missing-field) | ✅ covered | Trigger button `disabled` + `title` + italic `NoEmailAddressHint` beside it (`is_email_empty` pattern from `member_details.rs`); never a silent failed send (APMAIL-03). |
| populated / zero-one-many | timeline with 0/1/many entries + subject links (list-collection) | ✅ covered | Reuses unchanged `CommunicationTimeline` table (prop-driven), each row clickable → real stored body (D-06). |
| long-text | rendered sent body in detail panel (static-content) | 🧪 backstop | Long/HTML bodies render inside a bounded scroll container (`max-h-96 overflow-auto whitespace-pre-wrap`, established `MailJobDetail` pattern); needs a visual/held-out check that very long bodies and HTML content stay contained and do not overflow the panel/modal. |
