<objective>
Add the pure applicant template context builder `application_to_template_context` and its
`dummy_application_context` probe, extract a generic `validate_rendered(subject, body, &[Value])`
core so `validate_template` keeps its exact signature (member tests green), add
`validate_application_template`, and inject that validation into
`MailTemplateServiceImpl::create/update` for `template_type == "application"` so a broken applicant
template never persists (APTPL-01, APTPL-04). Finally prove the Zahlungserinnerung seed body is
strict-render-safe against the applicant context (completes APTPL-03).

Purpose: render templates against a real applicant context (separate from the member pool, D1)
with the correctly-formatted offener Betrag, and fail loudly-but-controlled on unknown/member-only
placeholders at author time instead of crashing under strict render at send time.
Output: 4 new template.rs symbols + a create/update validation injection + seed render proof.

RESEARCH DRIFT RESOLVED (D-10): the member flow does NOT validate at create/update today — member
templates are validated at SEND time (`genossi_mail/src/rest.rs:534-547`); `mail_template_service.rs`
create/update only sanitize HTML. So applicant-template validation at create/update is a NEW,
additive injection — do not "extend an existing create/update validation" (none exists). It keys off
`template_type == "application"` only, leaving the member path validation-free so member tests are
unaffected.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| applicant/config values → strict render | applicant fields + cooperative config are interpolated into template output as data |
| template author input → create/update | subject/body authored by board; validated (application type) before persist |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-03-01 | Tampering | template injection via applicant/config values | medium | mitigate | strict_env renders interpolated values as data, never re-evaluated as template markup; open_amount/bank_* are plain strings |
| T-30-03-02 | Denial of Service | strict-render crash at send time on unknown placeholder | high | mitigate | validate_application_template at create/update rejects unknown/member-only placeholders (BadRequest) so a broken template never reaches the send path (D-10) |
| T-30-03-03 | Information disclosure | member-pool data leaking into applicant context (DSGVO) | high | mitigate | Separate builder exposes ONLY applicant-provided fields + the cooperative's own bank data; no member-only keys defined, so member placeholders fail validation rather than leak (D1) |
</threat_model>
