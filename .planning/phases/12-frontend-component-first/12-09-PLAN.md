    **Schritt 1 — Component-Signatur erweitern:** Fuege den neuen Prop `reload_trigger: u64` HINZU (nach `phase: RepaymentPhaseTO`):

        on_paidout_request: EventHandler<Vec<RepaymentEntryTO>>,

    ) -> Element {

    **Schritt 2 — `use_effect` so erweitern, dass `reload_trigger` als implizite Read-Dependency mitgelesen wird.** In Dioxus 0.6 trackt `use_effect` automatisch alle gelesenen Signals — bei einem Prop reicht es, den Wert im Effect-Body zu lesen, damit ein Re-Run bei Aenderung getriggert wird. Pattern:

    ```rust
    // Pitfall 8: parallel MEMBERS-Refresh
    use_effect(move || {
        // Plan 12-09: reload_trigger als implizite Dep mitlesen → Counter-Aenderung loest Re-Run aus
        let _ = reload_trigger;  // explizites Read, damit Dioxus es als Dependency trackt
        spawn(async move {
            crate::service::member::refresh_members().await;
        });
        load_entries();
    });
    ```

    Das `let _ = reload_trigger;` ist KEIN No-Op fuer den Compiler: weil `reload_trigger: u64` ein Prop ist, das durch die Component-Funktions-Argumente sichtbar ist, wird jede Aenderung des uebergebenen Werts dazu fuehren, dass die Component re-runt (Funktion erneut aufgerufen). Damit feuert `use_effect` ebenfalls nochmal. Falls der Effect aus irgendeinem Grund nicht re-running (z.B. weil Dioxus den Effect Cached), wandle es alternativ in einen `use_memo`-getriggerten Branch:

    ```rust
    // Alternative (defensiv, falls use_effect-Capture-Verhalten zickt):
    let trigger = use_memo(move || reload_trigger);
    use_effect(move || {
        let _ = *trigger.read();   // tracked dep
        spawn(async move {
            crate::service::member::refresh_members().await;
        });
        load_entries();
    });
    ```

    Plan-Discretion: **bevorzugte Implementation = direkter `let _ = reload_trigger;`-Read im use_effect-Body.** Falls UAT zeigt dass der Reload nicht greift, auf `use_memo`-Variante umstellen — additiv ohne API-Bruch.

    **Wichtig — Reload-Cascade-Garantie (verbatim):**
    1. Vorstand klickt Submit im Add-Modal
    2. `RepaymentEntryAddModal::on_created` feuert in der Detail-Page
    3. Detail-Page: `entries_reload_trigger.set(current.wrapping_add(1))` — Counter inkrementiert

    6. In RepaymentEntryList's `use_effect` wird `let _ = reload_trigger;` als implizite Dep gelesen → Effect re-runt
    7. `load_entries()` wird erneut aufgerufen → neue Eintraege erscheinen in der Liste

    **Alternativ-Implementation-Diskussion (verworfen, nicht implementieren):**

    **Hinweis Reload-Counter-Wraparound:** `wrapping_add(1)` ist Defensive — ein u64 Counter wraparound passiert nach 18 Quintillion Inkrementen, in der Praxis nicht erreichbar. Pattern aber sauber.
