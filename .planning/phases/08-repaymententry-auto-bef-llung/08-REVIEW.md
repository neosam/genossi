# Phase 8: Code Review Report

**Reviewed:** 2026-05-31T00:00:00Z
**Depth:** standard
**Files Reviewed:** 16
**Status:** issues_found

## Summary

Phase 8 introduces the `RepaymentEntry` aggregate (DAO trait, SQLite impl, service trait,
service impl, REST handlers, types, DI wiring, migration) plus the auto-fill logic in
`RepaymentPhaseServiceImpl::open_repayment_phase` and the pending-validation in
`close_repayment_phase`. Architecture follows the established trait-boundary pattern,
audit-macro discipline is held (no direct `dao.create/update` outside the macros), and
unit-test coverage of the Edit-Matrix and batch-toggle paths is comprehensive.

Two BLOCKER bugs were found:

1. **Stale `version` UUID in PUT / batch / lifecycle responses** — `update_repayment_entry`,
   `batch_toggle_status`, `update_repayment_phase`, `open_repayment_phase`, and
   `close_repayment_phase` all return a domain object whose `version` field is the **pre-update**
   value. The DAO generates a fresh `version` UUID internally and writes it to the DB, but
   the service never reads it back. Any client using the response body's `version` for the
   next PUT will receive HTTP 409 "Version mismatch". The `MemberServiceImpl::update`
   already solves this with an explicit re-read (`member.rs:343 "Re-read to get the new
   version UUID generated by the DAO"`); RepaymentPhase/RepaymentEntry must do the same.

2. **`batch_toggle_status` 409 body for "entry not found"** treats a missing/soft-deleted
   entry id as a per-item conflict, but the helper text and the OpenAPI schema document
   404 semantics for "Not found". Mixing 404 semantics into a 409 response means a client
   that posts a stale id (e.g. a UI race) receives 409 with a body that mentions "entry
   not found" — the existing `BatchFailureResponse` schema in `genossi_rest_types/src/lib.rs`
   does not document this case, and the frontend will likely classify it as a domain
   conflict (e.g. "entry status changed") rather than as a stale-id problem. See WR-01
   for a milder reading; classifying as BLOCKER because the missing-id case can be
   triggered any time a client list is stale relative to the server.

The remaining findings cover redundant filters, dead branches, missing test coverage of
the staleness, log-noise around `SYSTEM` fallbacks, and minor style issues.

## Critical Issues

### CR-01: Service returns stale `version` UUID after DAO update (PUT response is unusable)

**File:** `genossi_service_impl/src/repayment_entry.rs:265-267` (update),
`genossi_service_impl/src/repayment_entry.rs:444-448` (batch_toggle), and
`genossi_service_impl/src/repayment_phase.rs:220-221, 354-355, 458-459`
(update_repayment_phase, open_repayment_phase, close_repayment_phase).

**Issue:**
`RepaymentEntryDaoImpl::update` (in `genossi_dao_impl_sqlite/src/repayment_entry.rs:136`)
generates `let new_version = Uuid::new_v4()` and writes it into the row, but the new UUID
is never propagated back to the service. The service returns `Ok(RepaymentEntry::from(&entity))`
where `entity.version` is still the **pre-update** value. A REST client that uses
`response.version` for a follow-up PUT will hit `WHERE id = ? AND version = ?` with the
stale UUID and receive `ConflictError("Version mismatch")` → HTTP 409. This breaks the
documented optimistic-locking contract for every PUT, every batch-toggle item, and every
lifecycle transition. The pre-existing `MemberServiceImpl::update` already encodes the
correct pattern:

```rust
// genossi_service_impl/src/member.rs:343-348 (existing solution)
// Re-read to get the new version UUID generated by the DAO
let updated = self
    .member_dao
    .find_by_id(item.id, tx.clone())
    .await?
    .ok_or(ServiceError::EntityNotFound(item.id))?;
```

Phase-7 inherited the same bug for `RepaymentPhaseServiceImpl` and Phase-8 carried it
forward. The E2E tests do not catch it because no test does a second PUT using the
version returned by the first PUT (`genossi_bin/tests/e2e_tests.rs:11334-11376` only
asserts the new status, never that `updated.version` works for a follow-up update).

**Fix:** After every `audited_update!` / `audited_delete!` call in `RepaymentEntryServiceImpl`
and `RepaymentPhaseServiceImpl`, re-read the entity inside the same transaction and use
the re-read value for the returned domain object:

```rust
// In update_repayment_entry, AFTER audited_update! (before commit):
let refreshed = self
    .repayment_entry_dao
    .find_by_id(id, tx.clone())
    .await?
    .ok_or(ServiceError::EntityNotFound(id))?;

self.transaction_dao.commit(tx).await?;
Ok(RepaymentEntry::from(&refreshed))
```

For `batch_toggle_status`, refresh each entry after its `audited_update!` (or push the
refreshed entity into `updated`) instead of `updated.push(RepaymentEntry::from(&entity))`.
Add an E2E regression test: PUT, take returned version, PUT again with that version,
assert 200 (not 409).

Alternative (preferred long-term): change the DAO `update` signature to return the new
`Uuid` (or accept a caller-supplied new version) so the service does not need a second
round-trip. That is a larger refactor, but the re-read fix is the minimal, in-scope
unblock.

### CR-02: `batch_toggle_status` maps "entry not found" to 409 Conflict (semantic clash with 404)

**File:** `genossi_service_impl/src/repayment_entry.rs:411-416`.

**Issue:**
```rust
let mut entity = self
    .repayment_entry_dao
    .find_by_id(*entry_id, tx.clone())
    .await?
    .ok_or_else(|| conflict_body(idx, *entry_id, "entry not found"))?;
```
A missing or soft-deleted entry id is reported as `ServiceError::Conflict` →
`RestError::Conflict` (HTTP 409) with `failure_reason: "entry not found"`. Every other
service method in this aggregate returns `ServiceError::EntityNotFound` for the same
condition (→ HTTP 404). The OpenAPI doc for `POST /api/repayment-entry/batch-status`
(`genossi_rest/src/repayment_entry.rs:260-266`) only documents 200 / 400 / 401 / 409 —
404 is intentionally omitted because the design says "first failing entry rolls back the
transaction" — but the `BatchFailureResponse` schema (`genossi_rest_types/src/lib.rs:1404-1411`)
does not call out that "entry not found" is a valid `failure_reason`. A frontend that
classifies 409 as "domain conflict (status changed, please refresh)" will silently fail
to surface the real cause when a UI race posts a stale id.

This is a correctness/UX defect, not a security issue, but it is reachable from normal
operation (any time the visible list is older than the server state — soft-delete from
another tab, etc.).

**Fix:** Either:

(a) Distinguish the two cases — return `ServiceError::EntityNotFound(*entry_id)` for the
None branch (which maps to 404) and keep the 409 conflict body only for "source status is
not Open/Contacted":

```rust
let mut entity = self
    .repayment_entry_dao
    .find_by_id(*entry_id, tx.clone())
    .await?
    .ok_or(ServiceError::EntityNotFound(*entry_id))?;
```

(b) Or document explicitly in `BatchFailureResponse` and the handler-OpenAPI that
`failure_reason` may include "entry not found" and that 409 in batch context covers both
domain conflicts and stale ids. Add 404 to the response list with a note about
all-or-nothing semantics.

Option (a) is the lower-surprise default and matches the rest of the aggregate.

## Warnings

### WR-01: `batch_toggle_status` returns stale version per entry, compounding CR-01

**File:** `genossi_service_impl/src/repayment_entry.rs:444`.

**Issue:** `updated.push(RepaymentEntry::from(&entity))` is called BEFORE the
transaction commits and uses the (still-old) `entity.version`. After the next iteration's
`audited_update!`, the DAO has written a new version to the DB for the previous entry —
but `updated[previous]` still carries the old one. The aggregated `Vec<RepaymentEntry>`
returned to the client therefore carries N stale versions (not just one as in CR-01).
This is CR-01's root cause applied N times.

**Fix:** Re-read each entry after its `audited_update!` (or batch-re-read all entries
after the loop and before commit). Same change applies to the loop body in
`RepaymentPhaseServiceImpl::open_repayment_phase` (auto-fill block) — those auto-filled
entries are not currently returned to the client, but if Phase 9 / 10 starts consuming
them via the lifecycle response, the same bug will surface.

### WR-02: `batch_toggle_status` second `target_status` check is dead code

**File:** `genossi_service_impl/src/repayment_entry.rs:391-403`.

**Issue:** After the `if input.target_status == RepaymentEntryStatus::PaidOut → return ...`
branch (line 382), the only remaining enum variants are `Open` and `Contacted`. The
follow-up `if !matches!(input.target_status, Open | Contacted)` is unreachable. The
guard is harmless today but will silently rot if a new status variant is ever added —
the new variant would be rejected here without an explicit reason in the error message
besides "Only Open and Contacted allowed". Either remove the second check or convert it
into a `match` on the full enum so the compiler enforces exhaustiveness when a fourth
variant lands.

**Fix:**
```rust
match input.target_status {
    RepaymentEntryStatus::PaidOut => {
        return Err(ServiceError::ValidationError(vec![ValidationFailureItem {
            field: Arc::from("target_status"),
            message: Arc::from(
                "PaidOut not allowed via batch-status; use Phase-9 mark_paid_out (D-07)",
            ),
        }]));
    }
    RepaymentEntryStatus::Open | RepaymentEntryStatus::Contacted => {}
    // forces an explicit decision when a new variant is added
}
```

### WR-03: Duplicate `deleted IS NULL` filter in close_phase pending validation

**File:** `genossi_service_impl/src/repayment_phase.rs:393-401`.

**Issue:** `find_by_phase_id` (Default-Impl in `genossi_dao/src/repayment_entry.rs:147-155`)
already filters `deleted.is_none()`. The service then does
`.filter(|e| e.deleted.is_none())` again on the result. The double filter is harmless
but misleads readers who may assume the DAO returns soft-deleted entries too.

**Fix:** Drop the second `.filter(|e| e.deleted.is_none())` and add a comment pointing at
the DAO's Default-Impl. Alternatively, document the intent of the redundant filter
("defense-in-depth in case a future DAO impl breaks the soft-delete invariant").

### WR-04: `share_count_to_pay_out as i64` performs a silent widening cast

**File:** `genossi_dao_impl_sqlite/src/repayment_entry.rs:102, 139`.

**Issue:** `let share_count = entity.share_count_to_pay_out as i64;` is an infallible
widening, so no data is lost. But the reverse direction in `TryFrom<&RepaymentEntryDb>`
(line 36) uses `i32::try_from(db.share_count_to_pay_out)` with a proper error path.
The asymmetry hides an invariant: the writer **must** stay within i32 because the
reader will fail on out-of-range. If the DAO ever starts accepting `i64`-input from
elsewhere (e.g. an admin-import path), the migration's `CHECK(> 0)` would still allow a
value > `i32::MAX`, and the next reader would hard-fail.

**Fix:** Either change the column documentation in the migration to "INTEGER, fits i32"
or add a debug-assert in the DAO write path:
```rust
debug_assert!(entity.share_count_to_pay_out > 0, "validated in service");
let share_count = entity.share_count_to_pay_out as i64;
```
The validator in `validate_entry_create` (service-layer) already enforces `> 0`, so the
debug-assert is the lighter touch and surfaces a bug fast if a future code-path skips
validation.

### WR-05: `current_user_id` runs **before** `check_permission` in every handler

**File:** `genossi_service_impl/src/repayment_entry.rs:105-112, 177-184, 276-283, 362-369`
(also pattern-replicated in repayment_phase.rs).

**Issue:** Every service method does `current_user_id(context.clone()).await?` BEFORE
`check_permission(ADMIN_PRIVILEGE, context).await?`. For an unauthenticated request,
`current_user_id` may itself error out (depends on `PermissionServiceImpl` semantics) —
which means an unauthenticated PUT first does a context lookup, then would have failed
permission anyway. This is a minor perf inefficiency and (more importantly) leaks the
identity-resolution path's failure mode to clients who shouldn't have gotten past
permission. Audit-log writes for these methods consume `user_id` via `unwrap_or_else(||
"SYSTEM".to_string())`, so if `current_user_id` returns `Ok(None)` (mock-auth) the
fallback hides the absence — but if it returns `Err`, the request is rejected for the
wrong reason.

**Fix:** Reorder to `check_permission` first, then `current_user_id`. Pattern (one line
swap):
```rust
self.permission_service
    .check_permission(ADMIN_PRIVILEGE, context.clone())
    .await?;
let user_id = self
    .permission_service
    .current_user_id(context)
    .await?
    .unwrap_or_else(|| "SYSTEM".to_string());
```

This also avoids the extra `context.clone()` if `check_permission` consumes the context
last (which it does).

## Info

### IN-01: `RepaymentEntryStatus::from_str` shadows the `std::str::FromStr` trait

**File:** `genossi_dao/src/repayment_entry.rs:31-41`.

**Issue:** Defining an inherent method named `from_str` that does not implement
`std::str::FromStr` invites confusion at call sites — `MyEnum::from_str("...")` resolves
to the inherent method here, but `"...".parse::<MyEnum>()` will not compile. The same
naming is used in `RepaymentPhaseStatus` and elsewhere in the codebase, so this is a
project-wide pattern. No behaviour change — calling out for consistency with future
trait-aware refactors.

**Fix (optional):** Either rename to `parse_str` or implement the trait:
```rust
impl std::str::FromStr for RepaymentEntryStatus {
    type Err = DaoError;
    fn from_str(s: &str) -> Result<Self, DaoError> { /* existing body */ }
}
```

### IN-02: Foreign-key constraints are documentary only — runtime not enforced

**File:** `migrations/sqlite/20260530203550_create_repayment_entry_table.sql:4-8, 42-43`.

**Issue:** The migration comment correctly notes that `PRAGMA foreign_keys=ON` is not
enabled. The service-layer enforces phase / member existence (D-11.1 + D-11.2). This is
acceptable but worth tracking in a separate ticket: enabling PRAGMA at startup would
catch any future code path that bypasses the service-layer guards (e.g. a backup-restore
script or a direct DAO unit test). The trade-off is migration churn — existing rows
would need cleanup if any FK is currently violated.

**Fix:** Track as roadmap item; consider enabling `PRAGMA foreign_keys=ON` in
`genossi_dao_impl_sqlite` connection setup with a defer-able FK mode for migrations
(`PRAGMA defer_foreign_keys = ON`).

### IN-03: `audited_update!` in `update_repayment_entry` does a redundant DB read

**File:** `genossi_service_impl/src/repayment_entry.rs:186-192` (service load) and
`genossi_service_impl/src/audit_macros.rs:47-50` (macro's internal load).

**Issue:** The service loads `entity` for the Edit-Matrix and version check (line 188);
`audited_update!` then loads `old` again to compute the diff. Both run inside the same
transaction so they see the same snapshot — the data is correct, but the second read
is wasteful. The code comments call this out (`WR-04: duplicate find_by_id`) and accept
it as a current trade-off. The same pattern exists in `repayment_phase.rs` and
`member.rs`.

**Fix (low priority):** Add an `audited_update_with_old!` variant that accepts the
already-loaded `old` entity and skips the internal lookup. Cross-cutting refactor —
park until the audit-macro API is revisited.

### IN-04: Test coverage gap — no E2E that re-uses the version returned by PUT

**File:** `genossi_bin/tests/e2e_tests.rs:11334-11421` (PUT tests).

**Issue:** Every Phase-8 E2E test that exercises PUT (`test_update_entry_status_open_to_contacted_succeeds`,
`test_update_entry_status_paid_out_returns_409`) uses the version from the **create**
response, not from a prior PUT response. CR-01 would surface immediately if any test did:

```rust
// after the first PUT:
let updated_version = updated.version.unwrap();
let resp2 = client.put(...).json(&UpdateRepaymentEntryRequest {
    share_count_to_pay_out: None,
    status: Some(RepaymentEntryStatusTO::Open),
    version: updated_version,
}).send().await.unwrap();
assert_eq!(resp2.status(), StatusCode::OK); // currently would be 409
```

**Fix:** Add a regression test as part of the fix for CR-01.
