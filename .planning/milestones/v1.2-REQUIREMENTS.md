**Core Value:** Genossenschaften verwalten ihre Mitglieder ohne Excel — verbandskonform, nachvollziehbar, mit weniger manueller Arbeit. v1.2 ergänzt die laufende Pflege während des Geschäftsjahres (Kündigung, Teil-Rückgabe, Übertrag, Aufstockung am Mitglied direkt) ohne v1.1's PaidOut-Cascade zu duplizieren.

## v1.2 Requirements

### Kündigung (CANC) — Voll-Rückgabe an Genossenschaft

- [x] **CANC-01**: Vorstand kann am Mitglied „Kündigung" auslösen (Single-Button auf Member-Detail-Page) — _Phase 15_
- [x] **CANC-02**: System berechnet H1/H2-Stichtag aus Willensbekundungs-Datum (H1 = Monat 1–6 → 31.12. aktuelles GJ; H2 = Monat 7–12 → 31.12. folgendes GJ) — _Phase 14 (Drift-Fix: war [ ]/Pending, technisch satisfied via `compute_effective_date` Pure-Function + 6 edge-case tests)_
- [x] **CANC-03**: System erzeugt eine `MemberAction::Austritt` mit `date = Willensbekundungs-Datum`, `effective_date = berechneter H1/H2-Stichtag`, `shares_change = 0` (Anteile bleiben bis zur Auszahlung unverändert) — _Phase 15_
- [x] **CANC-04**: `Member.exit_date` wird via existing `recalc_dates`-Hook automatisch aus der Austritts-Action gesetzt (keine direkte Mutation außerhalb von `recalc_dates`) — _Phase 15_
- [x] **CANC-05**: System erzeugt KEINE `MemberAction::Verkauf` und KEIN `RepaymentEntry` direkt; `current_shares` bleibt unverändert — v1.1's PaidOut-Cascade übernimmt Anteils-Reduktion und Verkauf-Action beim späteren Ausbezahlt-Toggle (Auto-Befüllung in `open_repayment_phase` picked den Member über `exit_date in fiscal_year` auf) — _Phase 15_
- [x] **CANC-06**: Vorschau-Confirm-Dialog zeigt Willensbekundungs-Datum, berechneten Stichtag, prognostizierte Ziel-Auszahlungsphase (fiscal_year) und Wirkungs-Timeline vor dem finalen Commit — _Phase 18_

### Teil-Rückgabe (PART) — Anteile zurück an die Genossenschaft, Mitgliedschaft bleibt

- [x] **PART-01**: Vorstand kann am Mitglied „Teil-Rückgabe" auslösen mit Anteils-Anzahl `n` (1..current_shares) und Willensbekundungs-Datum — _Phase 16 (Drift-Fix: war [ ]/Pending, technisch satisfied via REST POST /api/members/{id}/partial-repayment)_
- [x] **PART-02**: System berechnet H1/H2-Stichtag (Ziel-fiscal_year) analog Kündigung — _Phase 16 (Drift-Fix)_
- [x] **PART-03**: System erzeugt `RepaymentEntry` in der Ziel-Phase mit `share_count_to_pay_out = n`, Status `Open` — _Phase 16 (Drift-Fix)_
- [x] **PART-04**: System validiert `sum(open_entries.share_count for member in target_phase) + n <= member.current_shares` (Sum-Check verhindert Über-Rückgabe) — _Phase 16_
- [x] **PART-05**: System legt Ziel-RepaymentPhase automatisch an, falls für das berechnete fiscal_year noch nicht existent — _Phase 16 (Drift-Fix, Auto-Create-Variante B: Status=Open mit share_value aus Vorgänger oder `DEFAULT_SHARE_VALUE_CENT=10000`)_
- [x] **PART-06**: System erzeugt KEINE MemberAction und reduziert NICHT `current_shares` direkt (das macht v1.1's PaidOut-Cascade beim Ausbezahlt-Toggle) — _Phase 16 (Drift-Fix, grep-Gate: 0 direkte member_dao.update / audited_update!(member_dao) in partial_repayment)_

### Übertrag (TRSF) — Anteile an aktives Mitglied (Teil oder voll)

- [x] **TRSF-01**: Vorstand kann am Mitglied „Übertragen an Mitglied" auslösen mit Empfänger-Mitglied und Anteils-Anzahl `n` (1..source.current_shares) — _Phase 17_
- [x] **TRSF-02**: Übertrag ist sofort wirksam (kein H1/H2-Stichtag, da kein Geldfluss aus der Genossenschaft) — _Phase 17_
- [x] **TRSF-03**: System erzeugt 2 verlinkte MemberActions atomar in einer Tx: `MemberAction::UebertragungAbgabe(A: shares_change=−n, transfer_member_id=B.id)` + `MemberAction::UebertragungEmpfang(B: shares_change=+n, transfer_member_id=A.id)` — _Phase 17_
- [x] **TRSF-04**: System aktualisiert `Member.current_shares` für A (−n) und B (+n) atomar in derselben Tx — _Phase 17_
- [x] **TRSF-05**: Bei Voll-Übertrag (A.current_shares → 0 nach Übertrag) erzeugt System zusätzlich eine `MemberAction::Austritt` für A mit `date = Übertrags-Datum` und `effective_date = Übertrags-Datum`; `Member.exit_date` wird via `recalc_dates` automatisch gesetzt — _Phase 17_
- [x] **TRSF-06**: Empfänger-Search liefert nur aktive Mitglieder (`exit_date IS NULL AND id != source_id`) — neuer REST-Endpoint `GET /api/members/transfer-recipients?exclude_self={uuid}` — _Phase 14 (Drift-Fix: war [ ]/Pending, technisch satisfied via DAO+Service+REST+E2E full stack)_
- [x] **TRSF-07**: Self-Transfer ist verboten — Service-Layer-Guard liefert HTTP 400 bei `from_member_id == to_member_id` — _Phase 17_

### Aufstockung (UPGD)

- [x] **UPGD-01**: Vorstand kann am Mitglied „Aufstocken" auslösen mit Anteils-Anzahl `n` und Willensbekundungs-Datum — _Phase 15_
- [x] **UPGD-02**: Aufstockung ist sofort wirksam (kein H1/H2, kein Geldfluss) — _Phase 15_
- [x] **UPGD-03**: System erzeugt eine `MemberAction::Aufstockung(shares_change=+n, transfer_member_id=None)` und erhöht `Member.current_shares` um n atomar in einer Tx — _Phase 15_
- [x] **UPGD-04**: Aufstockung ist blockiert für gekündigte Mitglieder (`exit_date IS NOT NULL` → HTTP 400) — _Phase 15_

### UI

- [x] **UI-01**: Single-Button „Mitgliedschaft anpassen" auf Member-Detail-Page (nicht in Mitgliederliste — Audit-Bewusstsein durch extra Klick) — _Phase 18 (admin-only via `RequirePrivilege`)_
- [x] **UI-02**: `MembershipAdjustModal` als shared Component in `genossi-frontend/src/component/`; eine Modal mit Operation-Sub-Choice und vier Sub-Views — _Phase 18 (4-flat Sub-Choice-Variante)_
- [x] **UI-03**: Datepicker mit GJ-Bounds — erlaubt nur Daten im aktuell offenen GJ und im nächsten GJ (für H2-Wirksamkeit erforderlich) — _Phase 18 (`FiscalYearDateInput`-Component)_
- [x] **UI-04**: Vorschau-Section mit konkreter Zahlen-Anzeige vor Commit — _Phase 18 (alle 4 Sub-Views mit Live-Update-Preview)_

### Audit (AUDT)

- [x] **AUDT-01**: Alle v1.2-Operationen erzeugen Audit-Einträge via `audited_create!`/`audited_update!`-Macros (kein direkter DAO-Write außerhalb der Macros) — _Phase 15 (Pattern etabliert), durchgehend bis Phase 17_
- [x] **AUDT-02**: Übertrag-Pair (Aus + Ein) teilt sich gemeinsamen Process-String `process="member-adjust.transfer"` und kann via `/api/audit/verify` + Process-Filter als zusammenhängender Vorgang gefunden werden — _Phase 17 (TRANSFER_PROCESS shared by all 5 audited_*!-writes)_

### Permission & Validation (PERM)

- [x] **PERM-02**: Server-Layer validiert das Willensbekundungs-Datum: muss im aktuell offenen GJ oder nächsten GJ liegen — _Phase 15 (Pure-Function `validate_willensbekundung_date`)_
- [x] **PERM-03**: Empfänger beim Übertrag muss aktives Mitglied sein (`exit_date IS NULL`) — Service-Layer-Guard zusätzlich zum Search-Filter (TRSF-06) — _Phase 17 (HTTP 409 Conflict, ROADMAP-SC#4-Wortlaut sprach von 400 — Plan-Spec maßgeblich)_

## Out of Scope (Final — Begründung bleibt valid)

| Feature | Reason | Status nach v1.2 |
|---------|--------|------------------|
| Rückwirkende Erfassung in abgeschlossene GJs | sehr individuell; Vorstand nutzt bestehende manuelle MemberAction-UI | Bleibt out-of-scope |
| Übertrag an Mitgliedsantragsteller mit Auto-Vollmitgliedschaft | koppelt Application+Member+Anteile+Action atomar → zu komplex; bleibt als Seed | Bleibt out-of-scope, Seed aktiv |
| Storno-Knopf für ausgelöste Kündigungen | manuelle MemberAction-UI reicht als negative Gegenbuchung | Bleibt out-of-scope |
| Zwei-Stufen-Workflow (Antrag → Genehmigung) | One-Click mit Vorschau-Confirm ist Default; Vier-Augen ist v2 | Bleibt out-of-scope |
| `MemberAction::Verkauf`-Erzeugung durch v1.2 | v1.1's PaidOut-Cascade ist Single-Source-of-Truth; v1.2 erzeugt nur Intent-Datensätze | ✓ Eingehalten — grep-Gate bestätigt |
| `current_shares`-Reduktion durch v1.2 bei Kündigung/Teil-Rückgabe | v1.1's PaidOut-Cascade macht das beim Ausbezahlt-Toggle | ✓ Eingehalten (PART-06 + CANC-05) |
| Pessimistische Member-Locks während v1.2-Dialog | optimistic-locking + Re-Read reicht (Tech-Debt v1.3+) | Bleibt out-of-scope |
| Bulk-Operationen | nicht im Use-Case-Scope | Bleibt out-of-scope |
